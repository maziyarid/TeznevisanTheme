# TeznevisanTheme — Additional Issues Diagnosis

**Repository:** `maziyarid/TeznevisanTheme`  
**Audit branch:** `diagnosis/teznevisan-audit`  
**Scope:** Documentation only; no production code has been changed.

## Executive assessment

The repository currently contains two materially different copies of what appears to be the same WordPress theme: one at the repository root and another under `Teznevisan/`. This is not merely a backup-folder problem. It creates an unresolved packaging and execution question: depending on how the repository is zipped or deployed, WordPress may activate the root copy, the nested copy, or neither as intended. The two copies have different file inventories, different template implementations, different `functions.php` files, and different asset trees.

The supplied diagnosis identifies the most urgent runtime failures in the active/root code path: broken font paths, competing enqueue paths, jQuery dependency conflicts, hidden Chaty markup, probable syntax failure, omitted includes, mobile-menu defects, unsafe `.htaccess` handling, and build-output mismatch. This document deliberately records additional findings and risks beyond that list. Findings marked **confirmed** are supported by repository structure or code-search evidence. Findings marked **verify** require a local PHP/WordPress runtime check before remediation.

## 1. Repository and packaging defects

### 1.1 Two competing theme roots — confirmed

The root contains a complete-looking theme while `Teznevisan/` contains another theme copy. The root has files such as `archive-services.php`, `page-about.php`, `page-contact.php`, `single-services.php`, `theme-helpers.php`, and a large root `functions.php`; the nested copy has a different set including `front-page.php`, `author-profile.php`, `template-my-account.php`, and a different `functions.php`.

**Impact:** fixes can be applied to the inactive copy; deployment can package the wrong copy; templates can appear to “revert” after upload; asset URLs can resolve against a different theme directory than expected.

**Required decision:** choose one canonical theme root. Move the other copy outside the deployable theme tree or preserve it under an explicitly named archive that cannot be mistaken for the active source.

### 1.2 The copies have divergent templates — confirmed

Some files share identical blob SHAs, but important files do not. For example, the nested `functions.php`, `header.php`, `footer.php`, `style.css`, and template inventory differ from the root. This means the nested folder is not a harmless duplicate snapshot.

**Impact:** behaviour differs between copies, and a diff-based review of only one tree will miss defects in the other.

### 1.3 Theme installation contract is ambiguous — verify

A normal WordPress theme ZIP should contain one directory whose immediate contents include the theme stylesheet and `functions.php`. This repository currently has a repository root that itself resembles a theme and a second theme directory inside it. The deployment process is not documented well enough to establish which directory is zipped.

**Required test:** install a clean ZIP generated by the intended deployment command and record the exact directory WordPress detects. Add a packaging script or release instructions that fail if more than one theme root is present.

### 1.4 No canonical source-of-truth policy — confirmed

There is no evident repository-level rule preventing edits to both copies. The existing audit and plan documents do not resolve this architecture question.

**Impact:** merge conflicts, drift, unreviewed production changes, and false fixes.

## 2. Asset and build-system issues beyond font paths

### 2.1 No reliable manifest/version contract — confirmed/verify

`vite.config.ts` emits hashed files under `dist/js/[name]-[hash].js`, while PHP expects a fixed path under `assets/js/dist/main.js`. There is no demonstrated manifest-reading layer that maps Vite output to WordPress handles.

**Impact:** a successful build can still produce a site that loads old hand-written files, missing files, or duplicate bundles. Cache invalidation is also disconnected from the build output.

**Rewrite requirement:** choose one strategy: either ship stable, explicitly copied assets with a deterministic build step, or generate and consume a Vite manifest. Do not mix hashed build output with hard-coded paths.

### 2.2 Direct stylesheet markup bypasses WordPress dependency management — confirmed

The root `header.php` directly prints a Chaty stylesheet link and a favicon link. Any CSS loaded directly in the template bypasses WordPress’s enqueue order, dependency graph, versioning, conditional loading, and debugging tools.

**Impact:** duplicate CSS, ordering races, cache invalidation failures, and styles loading on admin or irrelevant templates if the markup is reused.

**Rewrite requirement:** move all CSS and JavaScript into one controlled enqueue layer; retain only essential metadata in the document head.

### 2.3 Asset loading is not conditional by feature — verify

The repository contains large Font Awesome, editor, TinyMCE, Chaty, accessibility, and page-specific assets. The current architecture appears to load several globally rather than only when required.

**Impact:** unnecessary requests, larger CSS/JS parse cost, and more opportunities for plugin conflicts. Profile the front page, archive, single post, admin, and editor screens separately.

### 2.4 Missing dependency and ordering tests — confirmed risk

The theme has multiple enqueue owners: root functions, nested functions, `inc/admin-functions.php`, `inc/classic-editor.php`, and direct template markup. There is no automated assertion that every dependency handle is registered before use or that each physical asset is loaded once.

**Required test:** capture the final `$wp_scripts` and `$wp_styles` queues in a development environment and fail QA on duplicate source URLs, unresolved dependencies, or front-end assets loaded in admin.

### 2.5 Cache-busting is inconsistent — verify

Some assets appear to use constants or fixed versions, while other direct links have no version. File modification times are not consistently used. This can make a corrected CSS or JavaScript file appear broken until multiple caches expire.

**Rewrite requirement:** define one version helper based on `filemtime()` for local production assets, with a safe fallback when the file is unavailable.

## 3. WordPress lifecycle and architecture

### 3.1 Theme logic is too concentrated in procedural files — confirmed

The root `functions.php` is very large, while the nested copy and `inc/` contain overlapping classes and procedural handlers. This makes load order, function ownership, and duplicate declarations difficult to reason about.

**Impact:** redeclaration fatals, hidden side effects, circular assumptions, and difficult rollback.

**Rewrite requirement:** use a small bootstrap `functions.php`, namespaced or uniquely prefixed modules, and an explicit ordered loader. Each module should have one responsibility.

### 3.2 Initialization is not visibly idempotent — verify

Multiple copies and multiple loader paths create a risk that classes are instantiated or hooks are registered more than once. Search results already show independent `wp_enqueue_scripts` registrations in root/nested files and `inc` modules.

**Required test:** enable `WP_DEBUG_LOG`, load front end and admin, and inspect duplicate callbacks, duplicate notices, repeated AJAX registration, and PHP redeclaration warnings.

### 3.3 Theme-only code is acting like a plugin — confirmed risk

The codebase includes AJAX handlers, admin menus, editor upload functionality, Telegram authentication, service metadata, custom search, ratings, likes/dislikes, contact/newsletter handling, and other persistent application behaviour.

**Impact:** switching themes can remove business-critical routes and data interfaces. It also makes the theme harder to test and increases the blast radius of a visual change.

**Architecture decision:** keep presentation and theme settings in the theme; move durable business logic to a plugin or an external service unless the explicit project requirement prohibits it. If the requirement is “no plugin,” document the operational risk and keep modules strictly isolated and migration-ready.

### 3.4 Activation/deactivation responsibilities are misplaced — confirmed risk

The supplied review notes `register_activation_hook()` in theme code. Theme activation hooks are not plugin activation hooks and should not be used as if they were a reliable migration mechanism.

**Impact:** rewrite rules, database setup, or default options may never be initialized as expected.

**Rewrite requirement:** use theme-switch hooks only for lightweight theme setup, and use an explicit admin migration routine or plugin-owned activation process for durable data operations.

### 3.5 Global filters are not scoped — confirmed risk

The theme forces the locale to `fa_IR` for all users. This is a global application decision, not a presentation-only setting.

**Impact:** English-speaking administrators, scheduled jobs, REST responses, and other users can receive Persian locale behaviour unexpectedly.

**Rewrite requirement:** use WordPress site language for the site-wide locale and user profile locale where supported; do not override `locale` globally from the theme.

## 4. AJAX, forms, and security risks beyond the supplied upload finding

### 4.1 Multiple unauthenticated state-changing endpoints — confirmed

Repository search finds unauthenticated handlers for post likes, dislikes, search, ratings, contact form, newsletter signup, Telegram authentication, and classic-editor upload. The upload endpoint is the clearest critical issue, but the other public endpoints also require individual threat modelling.

**Required audit per endpoint:** nonce or signed request validation, input sanitisation, authorization, object ownership, rate limiting, duplicate submission handling, response escaping, and abuse logging.

### 4.2 Nonce presence and verification are not demonstrated consistently — verify

The existence of `wp_ajax_nopriv_*` registrations does not prove that each handler verifies a nonce. Every public write endpoint must be checked at the handler, not assumed safe because it uses AJAX.

**Impact:** CSRF, forged reactions, spam submissions, account/session abuse, and database pollution.

### 4.3 Public search and authentication flows need abuse controls — confirmed risk

Search and Telegram authentication are exposed to unauthenticated requests. They need input length limits, query restrictions, rate limiting, replay protection, strict redirect validation, and safe error messages.

**Required test:** fuzz empty, oversized, malformed, encoded, repeated, and concurrent requests in a staging environment.

### 4.4 Contact/newsletter handlers may expose operational data — verify

The repository contains public contact and newsletter AJAX hooks. Confirm that responses do not return mail/API errors, internal paths, recipient addresses, database identifiers, or unsanitised user content.

### 4.5 Data storage and cleanup are undocumented — verify

Likes, dislikes, ratings, contact submissions, newsletter records, and authentication state require a documented storage, retention, deletion, and export policy. Theme switching should not orphan or silently delete this data.

## 5. Output, SEO, and content integrity

### 5.1 Template-level SEO is duplicated across archive templates — confirmed risk

Search results show repeated hidden Organization/Logo schema blocks in `category.php`, `tag.php`, and related templates, while the header also conditionally emits a title and Rank Math may emit metadata and schema.

**Impact:** duplicate or conflicting structured data, stale hard-coded organization details, and inconsistent entity identity across archives.

**Rewrite requirement:** define one SEO owner. The theme should provide semantic content and hooks; Rank Math should own title, canonical, social, sitemap, and schema output where active. Any theme-generated schema must be narrowly scoped and deduplicated.

### 5.2 Hard-coded organization and author identity — confirmed

Templates contain hard-coded Persian organization names, logo paths, and author presentation. These values should come from WordPress identity/settings or post author data, not repeated template literals.

**Impact:** rebranding, multisite use, localization, and media replacement become error-prone.

### 5.3 Manual title fallback is fragile — confirmed

The root header manually emits a `<title>` only when a Rank Math class is absent while `title-tag` support is active. Plugin detection by class name is brittle, and the fallback can conflict with other SEO systems.

**Rewrite requirement:** let WordPress `title-tag` handle the title and use documented SEO-plugin integration only for exceptional compatibility cases.

### 5.4 Structured data is likely semantically stale — verify

The presence of hidden schema blocks does not establish that article, organization, service, FAQ, or author properties are complete, accurate, or appropriate to each template. Validate generated JSON-LD with current schema testing tools after duplicate output is removed.

## 6. Accessibility and internationalisation

### 6.1 Accessibility behaviour is split across PHP, CSS, and JavaScript — confirmed risk

Accessibility assets and menu behaviour are registered in separate modules while the mobile menu also has its own script and CSS. The focus-trap leak described in the supplied findings is one symptom of the broader split ownership.

**Required test:** keyboard-only navigation, focus visibility, escape handling, focus restoration, reduced motion, screen reader labels, dialog semantics, and menu state announcements.

### 6.2 Hard-coded language and direction assumptions — confirmed

The root header manually adds `dir="rtl"` alongside `language_attributes()`, while the codebase contains LTR-specific selectors and globally forced Persian locale behaviour.

**Impact:** invalid/duplicate HTML attributes, inaccessible mixed-direction content, and inability to support an LTR administrative or site configuration cleanly.

### 6.3 Translation architecture is incomplete — verify

The repository has a `languages` directory, but all user-facing strings need an audit for text-domain consistency and translation wrappers. Hard-coded strings in PHP, JavaScript, HTML attributes, schema, and AJAX responses should be catalogued.

### 6.4 Form and error states need accessible semantics — verify

Contact, newsletter, rating, authentication, search, and editor flows should use labels, `aria-describedby`, live-region status messages, server-side errors, and keyboard-accessible controls. Do not rely on colour or JavaScript-only feedback.

## 7. Maintainability and template quality

### 7.1 Very large template files indicate copy-paste duplication — confirmed

Root templates such as `archive-services.php`, `page-categories.php`, `category.php`, `single.php`, `tag.php`, and `taxonomy.php` are unusually large. Repeated markup increases the chance that fixes are applied to one archive but not another.

**Rewrite requirement:** extract template parts for cards, metadata, breadcrumbs, pagination, schema, social actions, and empty states. Keep query logic separate from markup.

### 7.2 Template hierarchy is difficult to predict — confirmed risk

The repository includes generic and specialised files for services, categories, tags, pages, archives, and taxonomies, plus a nested competing set. A route-to-template matrix is required before rewriting.

### 7.3 Hard-coded fallback media paths are brittle — confirmed risk

Templates use direct theme asset paths and `onerror` fallbacks for logos. This bypasses the media library and can hide missing-asset defects instead of surfacing them during QA.

**Rewrite requirement:** use `get_custom_logo()`, attachment metadata, `wp_get_attachment_image()`, and escaped URLs with explicit missing-media fallbacks.

### 7.4 PHP escaping is inconsistent — verify

Large HTML/PHP templates and inline JavaScript need a complete escaping audit. Every URL, attribute, text value, JSON value, and HTML fragment must use the correct context-specific WordPress escaping function.

## 8. Performance and operational risks

### 8.1 Oversized assets are stored in the theme — confirmed

The repository contains a 13.8 MB Font Awesome JavaScript asset and zero-byte Font Awesome TTF files in the nested asset tree. Even if not currently enqueued, these files increase repository and deployment weight and can be accidentally loaded later.

**Action:** delete unused binaries after confirming no runtime dependency; keep only the required icon formats and glyph subset.

### 8.2 Inline scripts and styles make caching and CSP harder — confirmed risk

The nested footer contains inline scripts after `wp_footer()`, and the root header/footer include direct asset markup. Inline code complicates content security policy, caching, testing, and separation of concerns.

**Rewrite requirement:** move reusable JavaScript/CSS to versioned assets and pass data through `wp_localize_script()` or `wp_add_inline_script()` with strict JSON encoding only where necessary.

### 8.3 No performance budget or page-type acceptance thresholds — confirmed

There is no documented budget for CSS bytes, JavaScript bytes, image weight, request count, or interaction timing. Add budgets for front page, service page, archive, single post, search, and mobile menu interactions.

### 8.4 Cache and CDN behaviour is untested — verify

The unsafe `.htaccess` writer and direct font/CSS paths create deployment-specific behaviour. Test Apache, nginx, managed WordPress caching, CDN caching, compressed assets, and cache invalidation after a release.

## 9. Documentation reliability

### 9.1 Existing audit measurements should not be trusted without reproducible commands — confirmed

The repository’s `docs/AUDIT.md` contains measurements that conflict with the current repository listing and code review. File sizes, line counts, duplicate detection, and inclusion claims must be regenerated from a checked-out commit using reproducible commands.

**Required practice:** every numeric audit claim should include the commit SHA, command used, and path scope.

### 9.2 No runtime evidence bundle — confirmed

The diagnosis needs a staging evidence bundle: `php -l` results, WordPress debug log excerpts, browser console output, network waterfall, active theme path, loaded script/style handles, PHP/WordPress versions, and screenshots for desktop/mobile.

### 9.3 No release gate separating diagnosis from rewrite — confirmed

The branch created for this document must remain documentation-only. A later rewrite should use a separate implementation branch and a pull request whose checks include syntax, activation, asset loading, security, accessibility, and visual regression.

## 11. Verification commands and checks

Run these against the exact commit before rewriting:

```bash
php -l functions.php
php -l Teznevisan/functions.php
find . -type f -name '*.php' -print0 | xargs -0 -n1 php -l
find . -type f -name '*.php' -printf '%s %p\n' | sort -nr | head -50
sha256sum 404.php Teznevisan/404.php
npm run build
```

Then verify in a disposable WordPress installation:

1. Which theme directory WordPress detects and activates.
2. Whether activation produces PHP notices, warnings, fatals, or redeclaration errors.
3. The final front-end script/style handles and their resolved URLs.
4. Network status for every CSS, JavaScript, font, image, and favicon asset.
5. Whether public AJAX requests require and verify nonces where appropriate.
6. Keyboard/focus behaviour for menus, search, Chaty, dialogs, forms, and authentication.
7. Generated title, canonical, robots, Open Graph, schema, and sitemap output with and without Rank Math.
8. Behaviour after switching themes and after clearing page, object, browser, and CDN caches.

## 12. Rewrite sequence

1. Freeze the current commit and record runtime evidence.
2. Select and flatten the canonical theme root; preserve the other copy outside deployment.
3. Make `functions.php` a small bootstrap and load modules exactly once.
4. Create one asset manifest/enqueue system and remove direct template asset links.
5. Disable or secure all public AJAX handlers before restoring functionality.
6. Centralise theme setup, menus, widgets, customizer, media, locale, and SEO responsibilities.
7. Extract duplicated template parts and replace hard-coded identity/media values.
8. Rebuild mobile navigation and contact widgets with explicit accessibility state management.
9. Remove unused binaries and enforce build, lint, security, accessibility, and visual QA checks.
10. Only after the staging gates pass, prepare a separate implementation pull request.
